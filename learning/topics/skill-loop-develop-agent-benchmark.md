# Skill Loop 中只换 develop agent 的实测（同模型 Opus 5.5）

## 实验做法（可复用）

- 固定其他一切，只换 develop 步骤的 agent：同一个起点版本、同一份上轮核验反馈（共享基线：所有 agent 的第 1 轮拿同一次 selftest + 核验结果）、同一模型、同一判官、同一沙箱。
- 所有模型请求过一个本机计量代理（按 URL 里的 tag 区分每次 agent 调用），逐次记录 token、实际模型、耗时；不依赖各 agent 自己的用量统计。
- 被测版本做 2–3 次独立「平台运行 + 核验」复测，再比较均值；单次测量不足以比较。

## 结论

- 同模型、同输入下，各 agent 写出的改动方向一致（都做了需求里的同几件事）。按 Opus 5.5 判官，一轮后分数差约 13 分（74–87），排序在多次复测里稳定，并且和改动量同序；最快的 agent 多跑两轮也没追上。（第一次误用 DeepSeek-V4.1-Flash 判官时差 7–10 分、快的 agent 多跑一轮就"追平"，换判官后这个结论不成立。）
- 差距主要在效率和稳定性：同一轮 develop 耗时差 6–12 倍、输入 token 差 3–6 倍；有的 agent 4 小时跑不完一轮。耗时主要由每次调用的输出量（大部分是思考内容）决定，同一模型在不同 harness 下每次输出 535–3242 token 不等。
- 评测噪声：版本里有处在红线边界上的问题时（如从示例照抄的日期），单次测量标准差约 8–10 分，两个判官都会对同一份产物时判时不判「编造」红线；没有这类问题时，Opus 判官同一版本多次测量标准差 1–3 分。
- 判官决定了循环往哪改：同一批产物，Opus 比 DeepSeek 打分低、排序不同，还判出了 DeepSeek 漏掉的编造；按 DeepSeek 反馈改出的提升（+6.6 分）Opus 只认一半（+3.2 分）。判官模型要按实际使用的来配，换判官要重测。

## 踩坑

- **压缩摘要放在 assistant 角色会被模型不认。** OpenCode 压缩上下文后把摘要作为 assistant 消息、后接保留的工具调用；Opus 5.5 回答「我看不到之前的工作」并停下。4 条消息即可复现（user「What did we do so far?」→ assistant 摘要 → assistant → user 提问），messages / chat completions 两种接口都一样。对策：给足上下文窗口避免压缩，或换把摘要放在 user / system 角色的 harness。
- **框架给 agent 设的上下文窗口可能远小于后端实际能力**（配置 200K，实测后端能收约 97 万 token），窗口小会让 agent 在大 skill 上反复压缩、反复重读文件。
- **上游流在大请求（约 18–23 万 token）时偶发中断**，有的 agent（OpenCode、pi）直接退出，没有重试。
- **从 agent 会话库读用量会严重偏低**（实测低两个数量级），成本要按每次调用累加。
- **适配脚本自己加的超时会改变实验结论**：框架本身不设超时，最初设的 90 分钟兜底把 3 个慢 agent 打断，误判成失败；对照实验里任何额外限制都要和原框架对齐或单独标明。
- **判官模型配错会让整组结论跟着错**：需求里"在平台上用某模型跑"和"本地判官用某模型"是两回事，开跑前要逐项确认每个模型角色（develop / 平台执行 / 判官）。判官配错时，可以对保存下来的平台产物重新打分，不必重跑平台；但 develop 依据的反馈仍来自旧判官。
- **网关返回的 Claude 系用量里缓存数可能一直是 0**：经内部 OneAPI 调 Opus 时 cached_tokens、cache creation 字段全是 0，但同一请求重发时 cost 有时降到约 1/3，说明上游有缓存而接口不报。按「读 / 写 / 缓存」统计 token 时要注明缓存数的来源，准确数字查计费记录。
- **对照组的轮数和计量范围要一致**：中途为省时间只把慢的 agent 改成跑 1 轮，结果多轮结论只剩快的那一组数据；本地计量代理只看得到 develop 和判官，平台上按 skill 跑用例的用量要从平台返回的事件另算，否则一轮的成本会漏掉一块。
- **分数会奖励迎合检查脚本的写法**（避开误报的措辞、删掉会被判编造的示例日期），分数上升不一定代表分析质量上升。
- **Codex CLI 用非 OpenAI 的模型名时，行为取决于模型目录（model catalog）。** Codex 按模型名查元数据，决定系统提示词、工具和请求参数；查不到时提示 fallback metadata，改用内置的通用提示词、不提供 apply_patch 工具、不传 reasoning effort 和 verbosity、把多 agent 工具定义直接放进每次请求（同一句「只回复 OK」，首个请求 10.6K → 14.3K 输入 token）。内部 Codex 发行版自带的目录给 42 个非 OpenAI 模型套用同一份 GPT-5 系提示词，不是按模型单独调的。对比实验里 Codex 的结果对应「Codex + 这份目录」，要写进实验条件；目录里的上下文窗口也要按实验统一值覆盖。

## 下一步

- 如果要选 develop agent：先看完成率和每轮耗时 / token，再用多次复测比较质量。
- 判官侧：语义层多次判取中位数，或把红线判定改成需要多数一致，降低单次翻转。
