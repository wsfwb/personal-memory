# 决策记录：skill 自进化框架的网页层怎么做

## 1. 背景与核心问题
skill 自进化框架原本只有命令行（new / run / feedback / status）。产品同学要在网页上填需求文档和测试集、看循环进展，需求文档还可能放在知识库里。
问题：网页层要不要单独起一套服务（任务数据库、后台队列、前端工程），还是在现有 CLI 上包一层。

## 2. 备选方案对比

| 方案 | 优点 | 缺点 / 风险 |
| :--- | :--- | :--- |
| **A：薄壳（推荐）** 标准库 http.server + 原生 JS；建任务直接调 CLI 的函数；跑循环起 CLI 子进程；进度直接读流水线落盘的 state.json / run.json / result.json | 零新依赖；校验、目录布局、断点续跑全部复用，网页建的任务命令行照样能跑；状态只有一份（文件），不会出现"网页和命令行各说各话" | 没有登录和权限；多机部署要靠共享目录；进程管理靠 .lock + pid 文件，重启服务后要重新认领 |
| B：独立服务 + 数据库 + 任务队列 + 前端工程 | 可扩展多用户、多机 | 开发量数倍；两套状态要同步；流水线逻辑会被复制一遍进服务层 |
| C：在流水线进程内用线程跑循环 | 不用子进程 | 框架里 kill_all / STOP 是进程全局的，一个任务停止会影响其他任务；一个任务崩溃拖垮服务 |

## 3. 最终决定与理由
- **最终选择**：**方案 A**。
- **核心理由**：产品侧要的是"能用、看得见进展"，不是多租户系统；现有流水线已经把每一步的结果落盘（state.json 的 current/steps、selftest 的 run.json、evaluate 的逐用例 result.json），网页读这些文件就能做出实时进度，不必再造状态。
- 关键细节：
  - 跑循环的子进程 `start_new_session=True`，关掉网页服务不影响循环；停止 = `killpg(SIGTERM)`，CLI 把它当 Ctrl-C，状态停在当前步骤，再点继续从那一步接着跑。
  - 服务重启后靠任务目录的 `.lock`（flock 非阻塞探测）和 `.web_run.json`（pid、退出码）认出"还在跑 / 已结束 / 被别的终端跑着"。
  - 知识库文档不绑定具体平台：配置一条 `doc_fetch_command`（`{url}` 占位，标准输出是正文），链接记录在 task.yaml 的 source 里；没配就手动粘贴正文。
  - 读文件接口必须把路径解析到任务目录内（`resolve()` 后检查 parents），否则就是任意文件读取。

## 4. 预期结果与评判标准（供 `2026-12-27` 回看）
- **预期**：产品同学能不经我操作独立建任务、看进展、下载版本；没有出现网页与命令行状态不一致的问题。
- **如果未达预期怎么调**：若需要多人并发/权限，再在薄壳前加一层网关（登录 + 反向代理），不动流水线；若需要跨机器，把任务目录挂共享盘或把 run 接口改成远程调用。
